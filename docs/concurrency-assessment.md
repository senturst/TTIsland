# 服务端并发能力评估（20+ 同时在线）

> 评估基准：当前代码（2026-09-11）。结论先行：**20~50 人同时在线没有问题，100~200 人是单进程架构的舒适上限；真正的瓶颈不是数据库，是 AI 风味文本的生成速率与每动作的全量状态落盘。**

## 一、负载模型：这类游戏每秒到底有多少请求

文字回合制游戏 ≠ MMO。一个玩家的行为节奏：

| 动作 | 频率 | 说明 |
|---|---|---|
| `POST /api/run/action` | 3~6 秒 1 次 | 打字机动画 + 阅读文本天然限速 |
| `GET /api/run/active` | 进场时 1 次 | 恢复画面 |
| `GET /api/events/stream` (SSE) | 1 条长连接 | 世界事件播报，基本零流量 |
| AI 风味文本 | 后台异步 | 不阻塞玩家动作 |

**20 人同时在线 ≈ 4~7 QPS；50 人 ≈ 10~17 QPS；200 人 ≈ 40~70 QPS。**
这是非常轻的负载——单台普通 VPS 就能扛。

## 二、逐层拆解

### 1. SQLite（结论：不是瓶颈）

当前实现（`app/db/pool.py`）已经是正确姿势：

- ✅ WAL 模式：读写不互斥，读操作可无限并发
- ✅ `busy_timeout=5000`：写锁偶尔撞车时排队等待而非报错
- ✅ 每请求短连接 + `run_in_threadpool`：不阻塞事件循环
- ✅ `state_json` 整存整取，一个动作 = 1 次 UPDATE，无复杂多表事务

单次 action 的 DB 开销实测 <2ms（`get_active` 读 + `save` 写）。按最坏情况 70 QPS（200 人）算，写 QPS ≈ 70，SQLite WAL 在普通机械盘上都能扛 100+ 写/秒，SSD 上千级。

**唯一隐患**：`save()` 写的是整个 `state_json`（含 40 行日志、全量 level_map），单局后期 JSON 可能到几百 KB。20 人规模完全无感；200 人且都是老局时会放大磁盘写入量——届时优先裁剪 `log` 长度（现在没封顶）。

### 2. FastAPI / 事件循环（结论：不是瓶颈）

- 所有端点都是 `async`，同步 DB 调用都走了 `run_in_threadpool`
- AnyIO 默认线程池 40+ 线程，DB 调用单次 <2ms，不会打满
- SSE 长连接是内存中的挂起协程，单进程撑几千条没问题（`app/api/eventbus.py` 广播是内存 fan-out）

### 3. AI 风味文本（结论：**这是真瓶颈**，但已有保护）

`app/ai/limiter.py` 的并发闸门：`Semaphore(4)` + 0.5 req/s 令牌桶 + 每日预算 + 熔断。

20 人同时探索时，每个动作都可能触发 1~2 条风味文本生成。0.5 req/s 的生成速率意味着高峰期大量文本会**先返回模板、后台补 AI 版本**——这是设计好的降级路径（`render(wait=False)`），玩家只会看到模板文本，不会卡。

**保护已完备**，无需改动。若想让 20 人时 AI 文本命中率更高，把 `llm_max_concurrency` 从 4 提到 6~8 即可（DeepSeek API 侧没有并发限制压力）。

### 4. 内存（结论：不是瓶颈）

每局状态（含日志、地图）< 1MB。当前架构是**每请求从 DB 重建引擎**，内存里不常驻 run——200 个 active run 也只占磁盘不占内存。代价是每个 action 都要 `json.loads` 一次全量状态（<5ms），可接受。

## 三、风险清单（按优先级）

| # | 风险 | 触发条件 | 缓解 |
|---|---|---|---|
| 1 | **写并发撞锁** | 50+ 人且动作高度同步（如全服事件后齐刷刷行动） | WAL + busy_timeout 已兜底；真撞上表现为偶尔动作延迟 5s 而非失败 |
| 2 | **state_json 膨胀** | 单局 500+ 回合的挂机玩家 | `log` 加环形封顶（如保留最近 200 条），一行代码 |
| 3 | **限流误伤** | 玩家 1 分钟内点 60+ 次（连点） | `rate_action_per_min=60` 是按玩家独立计数，正常玩打不到；连点收到 429 是预期行为 |
| 4 | **uvicorn 单 worker** | 单 worker 默认单进程 | 回合制游戏 CPU 占用极低，单进程反而避免了 SQLite 多进程写锁；**不要**盲目加 workers |
| 5 | **SSE 断线重连风暴** | 服务重启瞬间几十个客户端同时重连 | 浏览器自动重连有随机退避，可忽略 |

## 四、结论与建议

**20 人并发：完全没问题，现状直接可跑。**

如果将来到 100+ 人，按顺序做这三件事（现在不用做）：

1. **日志环形封顶**：`state["log"]` 保留最近 200 条，防 JSON 膨胀（10 行代码）
2. **镜像列冗余查询**：`list_active`/管理后台已走镜像列，保持这个习惯
3. **热数据缓存**：`get_config()` 已是进程内单例，无需动

不建议做的：
- ❌ 换 PostgreSQL/MySQL——SQLite WAL 对这个量级绰绰有余，换库引入的运维成本远大于收益
- ❌ 加 uvicorn workers——SQLite 多进程写锁会让情况更糟
- ❌ 上 Redis——当前没有跨进程共享状态的需求

## 五、验证方法

上线后观察两个信号即可：

```bash
# 1. 日志里是否有 database is locked（WAL+busy_timeout 下不应出现）
grep -c "locked" logs/server.log

# 2. 动作接口的响应时间（admin 后台玩家列表刷新速度可间接感知）
```
